# Plan 4: Node.js Project Bootstrap

## Objective

Initialize `package.json` with `@supabase/supabase-js` as a server-side dependency and the correct Node.js engine constraint for Vercel's serverless runtime.

Purpose: The `api/_supabase.js` utility (Plan 03) imports `@supabase/supabase-js`. Without a `package.json` and installed dependency, Vercel will fail to build the API functions. This is the minimal infrastructure bootstrap required before any serverless functions can run.

Output: `package.json` at project root, `node_modules/` with Supabase client installed.

## Context

The current project has no `package.json` — it is a pure static site. This plan adds the minimum Node.js project config needed for Vercel serverless functions. The static HTML/CSS/JS files are not affected — they continue to be served as-is.

Key constraints (from CONTEXT.md and REQUIREMENTS.md):
- INFRA-01: `package.json` created with server-side dependencies (stripe, @supabase/supabase-js)
- The `stripe` SDK is included in INFRA-01 but is not used until Phase 5 — install it now alongside Supabase to avoid a separate `npm install` step later
- Node.js version: `22.x` (verified in RESEARCH.md — current LTS, confirmed available on Vercel Hobby)
- Use `"type": "module"` in `package.json` so `api/*.js` files can use ES module `import` syntax (`import { createClient } from '@supabase/supabase-js'`)

## Tasks

### Task 1: Initialize `package.json` and install dependencies

**Files:**
- `package.json` (created)
- `package-lock.json` (created by npm install)

**Action:**

Step 1 — Create `package.json` manually (do not use `npm init -y` which may set wrong values):

```json
{
  "name": "ruutdev-website",
  "version": "1.0.0",
  "description": "RuutDev website v2 — serverless API functions",
  "private": true,
  "type": "module",
  "engines": {
    "node": "22.x"
  },
  "scripts": {
    "dev": "vercel dev"
  },
  "dependencies": {
    "@supabase/supabase-js": "^2",
    "stripe": "^17"
  }
}
```

Notes:
- `"private": true` prevents accidental publish to npm
- `"type": "module"` enables `import`/`export` syntax in `api/*.js` files (required for `api/_supabase.js` and `api/contact.js` which use `export default` and `import { createClient }`)
- `@supabase/supabase-js: "^2"` — v2 is current stable major (RESEARCH.md Standard Stack)
- `stripe: "^17"` — current major as of 2025; pinned major, not minor, to avoid breaking changes
- `engines.node: "22.x"` — matches Vercel Hobby Node.js 22 runtime (RESEARCH.md verified)

Step 2 — Install dependencies:
```bash
npm install
```

Step 3 — Verify `node_modules/@supabase/supabase-js` exists:
```bash
ls node_modules/@supabase/supabase-js/package.json
```

Step 4 — Add `node_modules/` to `.gitignore` if not already present. Check `.gitignore` (created in Plan 03 Task 1, or create now if Plan 03 runs in parallel):
```bash
grep "node_modules" .gitignore || echo "node_modules/" >> .gitignore
```

Note: Plan 03 and Plan 04 both run in Wave 1 in parallel. If Plan 03 creates `.gitignore` first with the `node_modules/` entry, this step is a no-op. If Plan 04 runs first, add the entry here. Either way, `.gitignore` must contain `node_modules/` before committing.

**Verify:**
```bash
# package.json exists and is valid JSON — use grep (avoid require() in ESM project)
grep '"name"' package.json
grep '"node"' package.json
grep '"type"' package.json
# Expected: "name": "ruutdev-website", "node": "22.x", "type": "module"

# @supabase/supabase-js is installed
grep '"version"' node_modules/@supabase/supabase-js/package.json | head -1
# Expected: "version": "2.x.x"

# stripe is installed
grep '"version"' node_modules/stripe/package.json | head -1
# Expected: "version": "17.x.x"

# node_modules is gitignored
git check-ignore -v node_modules/
```

**Done:** `package.json` exists with correct content, `npm install` succeeded, `node_modules/@supabase/supabase-js` and `node_modules/stripe` are present, `node_modules/` is in `.gitignore`.

## Threat Model (ASVS L1)

### Assets Being Protected
- `package.json` dependency list — supply chain security
- `node_modules/` — must not be committed to git (large, contains build artifacts)

### Threats

| Threat | STRIDE | Component | Severity | Disposition | Mitigation |
|--------|--------|-----------|----------|-------------|------------|
| Dependency version too loose (^ or *) | Tampering | package.json | Low | Mitigate | Pinning to major version (`^2`, `^17`) limits breaking changes while `package-lock.json` (generated by npm install) locks exact versions for reproducibility |
| node_modules committed to git | Information Disclosure | .gitignore | Low | Mitigate | `.gitignore` must contain `node_modules/`; verified via `git check-ignore -v node_modules/` |
| Wrong Node.js engine causes runtime mismatch | Denial of Service | package.json engines field | Medium | Mitigate | `"engines": { "node": "22.x" }` matches Vercel Hobby Node 22 runtime (RESEARCH.md verified) |
| `"type": "module"` breaks existing CDN-loaded browser scripts | Tampering | package.json | Low | Accept | `"type": "module"` applies to `.js` files resolved by Node.js (i.e., `api/*.js` serverless functions). HTML pages use `<script src="...">` with browser globals — they are not affected by `package.json` type field. |

### Controls
- `package-lock.json` generated by `npm install` locks exact dependency versions
- `node_modules/` added to `.gitignore` before commit
- `"private": true` prevents accidental npm publish
</threat_model>
