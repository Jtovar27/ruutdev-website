# Plan 5: Supabase Provisioning + Vercel Environment Variables

## Objective

Provision the Supabase database (create project, run SQL schema, enable RLS, verify policies), set all required Vercel environment variables, and save the schema SQL as a committed file for future reference.

Purpose: Phase 2 API functions immediately need a live Supabase database with the correct schema and RLS. Vercel functions need environment variables to connect to it. Both must be done before Phase 2 begins.

Output: Live Supabase project with 4 tables + RLS. Vercel project with 7 env vars set. `supabase/schema.sql` committed as the schema source of truth.

## Context

This plan is Wave 3 — it runs after Plan 01 (directory structure), Plan 03 (api/_supabase.js knows what env vars to expect), and Plan 04 (package.json has @supabase/supabase-js installed).

This plan has two checkpoint tasks because Supabase provisioning and Vercel env var configuration require dashboard access — neither can be automated via CLI in this project's current setup.

Key constraints (from CONTEXT.md):
- D-12: Four tables: `reviews`, `portfolio`, `prices`, `content`
- D-13: RLS enabled on ALL tables at creation time (before any data is inserted)
- D-14: Anon key can only SELECT approved/visible rows; all writes require service-role key
- D-15: Supabase project in US East (us-east-1) to co-locate with Vercel iad1 functions
- D-17: Env vars: SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, SUPABASE_ANON_KEY, ADMIN_SECRET, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, WEB3FORMS_KEY

**RLS pitfall (RESEARCH.md Pitfall 4):** RLS must be enabled BEFORE any data is inserted. The `CREATE TABLE` statements below immediately follow with `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` — do not reorder or skip this step.

## Tasks

### Task 1: Commit `supabase/schema.sql` — the schema source of truth

**Files:**
- `supabase/schema.sql` (created)

**Action:**

Create the `supabase/` directory and write the complete schema SQL as a committed reference file. This file is run manually in the Supabase SQL editor (Task 2 checkpoint).

```sql
-- supabase/schema.sql
-- RuutDev v2 — Complete database schema
-- Run this in Supabase SQL Editor after creating the project.
-- IMPORTANT: Run in this exact order — RLS is enabled immediately after each table is created,
-- before any data is inserted. This is required to prevent RLS bypass on pre-RLS data.
-- Source: CONTEXT.md D-12, D-13, D-14 and RESEARCH.md Pattern 5

-- ────────────────────────────────────────────────────────────────────────────
-- reviews — Submitted by site visitors; moderated by admin before going public
-- ────────────────────────────────────────────────────────────────────────────
CREATE TABLE reviews (
  id         UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  name       TEXT        NOT NULL,
  role       TEXT,
  company    TEXT,
  rating     INT         NOT NULL CHECK (rating BETWEEN 1 AND 5),
  text       TEXT        NOT NULL,
  status     TEXT        NOT NULL DEFAULT 'pending'
                         CHECK (status IN ('pending', 'approved', 'rejected')),
  created_at TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE reviews ENABLE ROW LEVEL SECURITY;
-- Anon users can only read approved reviews
CREATE POLICY "Public read approved reviews"
  ON reviews FOR SELECT
  USING (status = 'approved');

-- ────────────────────────────────────────────────────────────────────────────
-- portfolio — Projects managed by admin; supports bilingual content + tagging
-- ────────────────────────────────────────────────────────────────────────────
CREATE TABLE portfolio (
  id             UUID      PRIMARY KEY DEFAULT gen_random_uuid(),
  title          TEXT      NOT NULL,
  title_es       TEXT,
  description    TEXT,
  description_es TEXT,
  url            TEXT,
  image_url      TEXT,
  tags           TEXT[],
  visible        BOOLEAN   NOT NULL DEFAULT true,
  sort_order     INT       NOT NULL DEFAULT 0,
  created_at     TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE portfolio ENABLE ROW LEVEL SECURITY;
-- Anon users can only read visible projects
CREATE POLICY "Public read visible portfolio"
  ON portfolio FOR SELECT
  USING (visible = true);

-- ────────────────────────────────────────────────────────────────────────────
-- prices — Pricing packages; admin editable; replaces hardcoded HTML prices
-- ────────────────────────────────────────────────────────────────────────────
CREATE TABLE prices (
  id          UUID      PRIMARY KEY DEFAULT gen_random_uuid(),
  plan_key    TEXT      UNIQUE NOT NULL,
  label_en    TEXT      NOT NULL,
  label_es    TEXT,
  amount_usd  INT       NOT NULL,
  stripe_link TEXT,
  features_en TEXT[],
  features_es TEXT[],
  visible     BOOLEAN   NOT NULL DEFAULT true,
  updated_at  TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE prices ENABLE ROW LEVEL SECURITY;
-- Anon users can read all visible pricing packages
CREATE POLICY "Public read visible prices"
  ON prices FOR SELECT
  USING (visible = true);

-- ────────────────────────────────────────────────────────────────────────────
-- content — General site copy (hero headline, service descriptions, etc.)
--           key = content identifier, value_en/value_es = bilingual text
-- ────────────────────────────────────────────────────────────────────────────
CREATE TABLE content (
  key        TEXT        PRIMARY KEY,
  value_en   TEXT        NOT NULL,
  value_es   TEXT,
  updated_at TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE content ENABLE ROW LEVEL SECURITY;
-- Anon users can read all content (no filtering — all content is public)
CREATE POLICY "Public read all content"
  ON content FOR SELECT
  USING (true);
```

**Verify:**
```bash
# File exists
ls supabase/schema.sql

# Contains all 4 CREATE TABLE statements
grep "CREATE TABLE" supabase/schema.sql | wc -l
# Expected: 4

# All 4 tables have RLS enabled
grep "ENABLE ROW LEVEL SECURITY" supabase/schema.sql | wc -l
# Expected: 4

# Status check constraint exists on reviews
grep "status IN" supabase/schema.sql
```

**Done:** `supabase/schema.sql` exists with complete DDL for all 4 tables, RLS enabled on each, and correct SELECT policies.

### Task 2 (checkpoint): Create Supabase project and run schema SQL

**Type:** checkpoint:human-verify

**What was built:**
- `supabase/schema.sql` committed in Task 1 — use this file as the input for the SQL editor

**How to set up:**

1. Go to https://supabase.com/dashboard and sign in (or create a free account).

2. Create a new project:
   - Name: `ruutdev`
   - Organization: your org
   - Region: **US East (us-east-1) — Virginia** (per CONTEXT.md D-15 — co-locate with Vercel iad1)
   - Database password: use a strong random password (save it, but it is not an env var we use directly)
   - Wait for project to finish provisioning (~1-2 minutes)

3. Navigate to **SQL Editor** → **New Query**.

4. Paste the entire contents of `supabase/schema.sql` and click **Run**.

5. Verify the tables were created — go to **Table Editor** and confirm you see: `reviews`, `portfolio`, `prices`, `content`.

6. Verify RLS is enabled — run this SQL in the SQL editor:
   ```sql
   SELECT tablename, rowsecurity
   FROM pg_tables
   WHERE schemaname = 'public';
   ```
   All 4 tables must show `rowsecurity = true`.

7. Verify anon read policy works correctly — run this SQL:
   ```sql
   -- Test as anon role: should return 0 rows (no approved reviews exist yet)
   SET ROLE anon;
   SELECT * FROM reviews;
   -- Expected: 0 rows (policy filters on status='approved', none exist)

   SET ROLE authenticated;
   -- Reset role
   ```

8. Collect environment variable values — go to **Project Settings → API**:
   - Copy **Project URL** → this is `SUPABASE_URL`
   - Copy **anon public** key → this is `SUPABASE_ANON_KEY`
   - Copy **service_role** key (reveal it) → this is `SUPABASE_SERVICE_ROLE_KEY`

**Resume signal:** Type "approved" once tables are created, RLS is confirmed enabled on all 4 tables, and you have the 3 Supabase env var values ready. Include any SQL errors if tables failed to create.

## Threat Model (ASVS L1)

### Assets Being Protected
- Supabase database — contains site data (reviews, portfolio, pricing, content)
- Row Level Security — prevents unauthorized reads/writes via the anon key
- Vercel environment variables — credentials that must never appear in client-side code or git

### Threats

| Threat | STRIDE | Component | Severity | Disposition | Mitigation |
|--------|--------|-----------|----------|-------------|------------|
| RLS disabled or misconfigured — anon reads pending reviews | Information Disclosure | Supabase RLS policies | High | Mitigate | Schema SQL enables RLS immediately after CREATE TABLE. Verification step: `SET ROLE anon; SELECT * FROM reviews` must return 0 rows. SQL runs in checkpoint before any data is inserted. |
| Service-role key exposed in browser | Information Disclosure | Vercel env vars | Critical | Mitigate | SUPABASE_SERVICE_ROLE_KEY is only in server-side `api/_supabase.js`. Never referenced in HTML pages or `assets/js/main.js`. Vercel does not expose server env vars to client bundles. |
| Supabase project in wrong region — high latency | Denial of Service (perf) | Supabase project setup | Low | Mitigate | Checkpoint instructions specify US East (us-east-1 Virginia) to co-locate with Vercel iad1 (CONTEXT.md D-15). Latency difference is ~5ms vs ~150ms for wrong region. |
| ADMIN_SECRET is weak or guessable | Elevation of Privilege | Vercel env var ADMIN_SECRET | High | Mitigate | Checkpoint instructs user to generate with `openssl rand -base64 32` (256-bit entropy). Note: admin auth enforcement is Phase 3 work — secret is provisioned here but not enforced until ADMN-02. |
| supabase/schema.sql committed with real credentials | Information Disclosure | supabase/schema.sql | Critical | Mitigate | schema.sql contains only DDL (CREATE TABLE, ALTER TABLE, CREATE POLICY) — no credentials, no connection strings, no API keys. Safe to commit. |
| status CHECK constraint bypass via SQL injection | Elevation of Privilege | reviews table | Medium | Accept | ASVS L1 requires server-side validation (covered in Phase 4 API-04 review submission); CHECK constraint is a defense-in-depth DB layer. No user input reaches DB in Phase 1. |
| Anon key accidentally set to service-role key in env vars | Elevation of Privilege | Vercel env vars | High | Mitigate | Checkpoint table clearly distinguishes SUPABASE_ANON_KEY (anon public) vs SUPABASE_SERVICE_ROLE_KEY (service_role) with source descriptions. Keys have different prefixes and lengths. |

### Controls
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` runs immediately after each `CREATE TABLE` — no window where RLS is off
- Each table has a `CREATE POLICY ... FOR SELECT` that limits anon reads to approved/visible rows
- `supabase/schema.sql` contains zero credentials — safe to commit as schema documentation
- ADMIN_SECRET generated with `openssl rand -base64 32` for 256-bit entropy
- STRIPE_WEBHOOK_SECRET set as placeholder now; real value added in Phase 5 when the webhook endpoint exists
